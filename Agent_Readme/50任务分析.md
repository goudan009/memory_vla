# Agent 任务书：B1K-2025 全部 50 任务的能力需求分析与分类统计

## 一、任务目标

基于现有 B1K-2025 官方任务定义、10,000 条成功示教数据（以实际可读取数量为准），以及项目中已经部署的 VL 视频分析模型，对全部 50 个任务开展系统性分析。

**目标不是评估当前 GR00T 的性能，而是先弄清楚 B1K 中各任务到底需要机器人具备什么能力，以及哪些能力适合通过 Memory 或 Body 模块改进。**

最终形成：

1. 50 个任务的能力分类表。

2. 各能力类别在 50 任务中的数量与占比。

3. 各任务内部，不同能力对应阶段的数量与占比。

4. 历史记忆需求的细粒度分类。

5. Memory 和 Body 适合验证的任务排行榜。

6. 未来可以直接用于工作台分阶段评估的任务配置草案。

本任务暂时不修改 GR00T、Memory 或 Body 网络，不启动模型训练。

---

## 二、首先调查现有数据与工具

检查本地项目的：

- B1K-2025 50 个任务的官方定义、名称、语言指令和成功条件。

- 每个任务的官方示教、视频、动作与机器人状态。

- 现有 VL 分析模型的接口及视频输入能力。

- 之前 Task 40 的任务分析和工作台 VL 诊断功能。

- 是否能读取示教中的场景、物体、关节和任务状态。

必须从真实任务注册表获取 50 个任务，不得凭记忆补全任务清单。

记录每个任务实际可读取的示教数量与数据完整性。

---

## 三、建立统一的能力分类体系

使用以下七个一级类别，可多标签分类。

| ID  | 能力类别      | 主要考察内容                 |
| --- | --------- | ---------------------- |
| A   | 任务顺序与规划   | 操作前置条件、顺序选择、阶段切换       |
| B   | 历史记忆与状态追踪 | 出视野物体状态、已完成操作、历史信息利用   |
| C   | 导航与空间定位   | 跨区域移动、目标查找、重新定位        |
| D   | 本体结构与协调   | 底盘、躯干、双臂运动学关联、可达性、协调动作 |
| E   | 精细操作与接触   | 抓取、放置、开门、按压、接触控制       |
| F   | 失败检测与恢复   | 判断操作是否成功、重新尝试、错误恢复     |
| G   | 视觉理解与目标识别 | 物体识别、状态识别、目标定位         |

每个任务可以对应多个类别。

进一步细分关键能力：

### B：历史记忆

- B1：目标曾出现但离开当前视野

- B2：需要追踪此前操作是否完成

- B3：重复物体、相似位置的历史消歧

- B4：跨工位任务状态保持

- B5：操作结果未明确确认，需要利用后续观测判断状态

### D：本体与协调

- D1：底盘与机械臂协调

- D2：躯干与机械臂协调

- D3：左右臂协同

- D4：构型相关可达性

- D5：本体状态与历史信息联合决策

### F：恢复

- F1：导航失败后的恢复

- F2：抓取或接触失败后的恢复

- F3：阶段执行失败后的重新决策

- F4：重复无效操作的识别和退出

注意：能力类别描述任务要求，不代表某种模块已经能够解决该问题。

## 四、逐任务、逐阶段分析

### 4.1 建立任务结构

对每个任务，首先阅读官方任务定义及指令，再分析成功示教。

输出：

- 任务目标

- 关键物体和场景

- 主要操作阶段

- 各阶段的前置条件

- 各阶段的物理完成条件

- 允许的阶段转换关系

- 对应能力标签

不要强制将所有任务划分成固定数量的阶段。

对于允许并行、重复或不同执行顺序的任务，应使用有向阶段图，而不是强行规定单一线性序列。

### 4.2 使用 VL 模型分析示教

先在每个任务中选择 3～5 条代表性示教进行初步分析。

对于存在不同操作顺序、不同物体位置或分析不确定的任务，增加示教数量并记录采样依据。

VL 模型需要识别：

- 机器人正在操作什么物体

- 进行了哪些动作

- 哪些状态发生了变化

- 是否发生跨区域移动

- 哪些动作存在明显前置条件

- 哪些历史状态在后续阶段可能仍然重要

必须结合官方任务条件、动作和可读取的物理状态进行交叉验证。

不要让 VL 仅根据视频生成一段泛泛的任务描述。

### 4.3 判断每个阶段需要哪些能力

每个阶段可具有多个能力标签。

分别记录：

- 是否涉及任务顺序选择

- 当前观测是否足以作出决策

- 是否存在需要追踪的历史状态

- 是否存在明显的多部件协调要求

- 是否需要精细接触操作

- 是否可能发生需要恢复的失败状态

同时给出可追溯证据：

`task_id、episode_id、stage_id、time_range、evidence_source、reason、confidence`

对无法确认的分类标记为 `unknown`，不强行分类。

## 五、特别重要：严格区分历史需求

不能因为某个任务时间长、有多个阶段，就自动判断它需要 Memory。

例如 Task 40：

- 初始状态选择先去微波炉：主要属于任务顺序决策，不能直接认定必须使用历史。

- 打开微波炉后，走到爆米花区域：可能需要记住微波炉门的状态。

- 微波炉门就在当前画面中：门是否打开可能直接通过当前视觉判断。

- 微波炉已离开视野，随后需要决定能否放入爆米花：属于历史需求候选场景。

对每个历史需求候选阶段，记录：

1. 需要记住的具体状态是什么？

2. 该状态曾经在哪些观测时刻出现？

3. 当前三相机、机器人状态和任务指令是否已经提供同样信息？

4. 如果没有历史，是否存在不同隐藏状态对应不同正确动作的可能？

5. 是否有原始数据或任务定义支持上述判断？

分类结果分为：

- `H0`：未发现明确历史需求

- `H1`：历史可能提供辅助信息

- `H2`：存在较强的历史依赖候选证据

- `HU`：证据不足，无法判断

注意：H2 不是已经从实验上证明 Memory 必不可少。严格证明还需要固定当前输入、改变历史信息的受控实验。

在成功示教中能够发现潜在历史需求，但不能直接判断模型遭遇失败时的恢复能力。

## 六、统计各类能力的占比

需要提供两个层次的统计结果。

### 6.1 任务级统计

例如：

| 能力     | 涉及任务数 | 占 50 任务比例 |
| ------ | ----- | --------- |
| 历史记忆   | N     | N/50      |
| 任务顺序规划 | N     | N/50      |
| 导航     | N     | N/50      |
| 本体协调   | N     | N/50      |
| 精细操作   | N     | N/50      |
| 失败恢复需求 | N     | N/50      |
| 视觉理解   | N     | N/50      |

必须真实统计，不允许预填比例。

多标签占比允许总和超过 100%。

### 6.2 阶段级统计

统计全部已确认阶段中：

- 涉及历史状态追踪的比例

- 涉及任务顺序决策的比例

- 涉及跨区域移动的比例

- 涉及本体协调的比例

- 涉及精细操作的比例

- 涉及潜在失败恢复需求的比例

分母为已分析的有效阶段数量。

同时按每个任务分别汇总，避免阶段特别多的任务在整体统计中过度占权重。

不要把“某阶段需要恢复能力”直接统计成“该阶段实际发生恢复失败的概率”。

**只使用成功示教时，不得输出 GR00T 各类错误的真实发生率。** 实际错误占比需要后续结合失败 Rollout 单独统计。

## 七、形成 Memory / Body 的任务适用性矩阵

对全部 50 个任务生成一张总表。

每一行至少包含：

- Task ID、任务名称

- 示教数量

- 主要任务阶段数

- 能力类别 A～G

- 历史需求等级 H0/H1/H2/HU

- 历史依赖候选阶段及证据

- 本体协调需求类型 D1～D5

- 精细操作难点

- 可能的恢复需求

- 推荐的主要评价指标

- 分类置信度

- 是否需要人类专家复核

分别筛选：

**Memory 优先验证任务**

重点选择具有出视野状态追踪、重复物体消歧、跨工位历史决策等特点的任务。

**Body 优先验证任务**

重点选择具有运动学构型差异、多部件协调和构型条件化检索潜力的任务。

注意：B1K 当前主要使用固定机器人本体，不能仅根据任务分类证明跨本体泛化优势。

**Memory + Body 联合验证任务**

选择同时具有历史需求和构型相关决策需求的任务，作为后续联合方法的重点候选。

排行榜使用明确、可解释的规则，同时展示各项依据，而不是只让 VL 模型主观打分。

## 八、为后续细粒度评价建立指标映射

对每种能力，提出可以实际测量的指标。

至少包括：

- 任务顺序：错误阶段转换率、关键决策正确率

- 历史记忆：历史依赖决策正确率、正确/错误历史性能差异

- 导航：目标区域到达率

- 本体协调：可达性或运动约束违规率、相关操作阶段成功率

- 精细操作：抓取、开门、放置等物理完成率

- 失败恢复：可确认失败后的恢复成功率

- 整体任务：完整成功率

区分三种状态：

1. 当前数据可以直接计算。

2. 需要增加 Rollout 仿真日志才能计算。

3. 需要人工确认、模型干预或额外实验才能计算。

不允许把候选指标伪装成已经得到的性能结果。

这些指标以后要用于现有工作台的模型对比系统。

## 九、为其他任务生成可复用的阶段配置

基于 Task 40 的设计，为其余 49 个任务输出阶段配置草案。

建议使用 YAML 或 JSON，包括：

- 任务 ID

- 阶段列表及阶段依赖关系

- 前置条件

- 完成判据

- 能力标签

- 可关联的仿真状态

- 可观察的失败事件

- VL 分析提示

- 需要人工核查的字段

所有自动生成的阶段配置默认标记为 `draft`。

**人类专家主要负责确认任务语义、阶段顺序、前置条件与完成判据，不要求逐帧标注全部示教。**

未经专家确认的配置不进入正式论文统计或官方性能评估。

Task 40 作为首个完整验证的任务，其余任务先完成统一分类和配置草案即可。

## 十、质量控制与人工核查

先选择 Task 40 和另外 4 个具有不同能力特征的任务进行试分析，确认分类规则能够稳定工作，再批量处理全部 50 个任务。

要求：

1. 同一套分类定义适用于全部任务。

2. 不允许任务名称直接决定全部能力标签。

3. 关键结论必须关联任务定义或示教证据。

4. 对存在歧义的场景进行多段视频复核。

5. 采用少量人工核查评估 VL 分类可靠性。

6. 记录证据不足、不可识别或存在不同解释的情况。

7. 保留原始分析结果与人工修订记录。

优先抽查历史依赖、前置条件和任务状态判断相关的分类，因为这些直接影响后续 Memory 论文实验。

## 十二、执行与验收要求

分三个阶段执行：

**P0：分类规则试运行**

先分析 5 个代表性任务，检查能力定义是否合理，特别是历史需求判定。

**P1：50 任务批量分析**

复用已有 VL 模型，利用视频片段采样、结果缓存和结构化输出完成全量任务分类，不必对 10,000 条轨迹逐帧调用 VL。

确保最终覆盖官方全部 50 个任务；对无法分析的任务单独报告原因。

**P2：统计汇总和科研任务推荐**

生成能力分布、阶段配置草案和 Memory / Body 候选任务清单，并提出下一阶段适合做成功率与历史干预实验的具体任务。

最终验收时，必须能够回答：

1. B1K 50 任务分别需要哪些能力？

2. 各类能力涉及多少任务，占比多少？

3. 哪些任务具有较强的历史依赖候选证据？

4. 哪些任务具有明显的本体协调需求？

5. 哪些任务同时适合 Memory 和 Body？

6. 现有成功示教能够支持哪些结论？

7. 哪些结论仍需要失败 Rollout 或受控实验？

8. 哪些任务最值得优先开展后续论文实验？

**本阶段不修改模型、不补采数据、不重新训练 50 任务。重点是形成一套可以复用、可核查、真正服务于科研实验设计的任务能力分类体系。**
