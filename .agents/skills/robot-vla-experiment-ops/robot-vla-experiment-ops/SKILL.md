# 机器人 VLA 科研实验执行规范

此 Skill 管理**如何执行实验**，不决定**做什么科学实验**。实验任务书只需写模型/任务/数据/对比/训练预算/验收指标；通用训练、评估、硬件、工作台和报告规则统一引用本 Skill。

## 一、优先级与启动检查

1. **指令优先级：**用户当前明确要求与当前实验任务书中的特定配置 > 本 Skill 的通用默认流程。任务书未指定的超参以锁定的官方方法/仓库配置为依据，**禁止用 Skill 中的例子擅自覆盖模型训练配方**。来源冲突先查源代码、配置和用户要求；影响可比性时报告差异再执行。
2. **审计现有环境：**先定位仓库根、现有训练/推理/评估工作台、实验目录、GPU 和正在运行的作业；确认配置与权限，禁止假设端口、可执行命令或远端路径存在。
3. **划清任务身份：**标记实验编号、Git commit、模型名称/初始化权重、数据清单、任务种子、正式训练/正式评估/Agent 诊断类别。对先前结果只读，不覆盖已封存原始数据。
4. **V1/V2边界：**若本次明确要求 V1 忠实复现 MemoryVLA，仅允许 GR00T 的必要工程适配；方法创新放在 V2。不要把零训练参考权重、旧 Residual V1、忠实复现 V1 与未来 V2 混成同一个实验组。

## 二、训练身份与 checkpoint 强制命名（优先级高）

**模型版本（`v1`、`v2`）与测试序号（`test01`）、实验编号（`exp12`、`exp13`）、独立训练次数（`run001`）是四个不同字段，禁止混写。** 特别禁止因为执行第12组实验就把模型称为 `V12`，或把 `V10` / `V11` 当作新增模型版本。保留用于实验或评估的 checkpoint 统一采用：

`v{模型版本}__test{测试序号}__exp{实验编号}__run{独立训练次数}__step{累计optimizer步数}`

- 例如：`v1__test01__exp12__run001__step002000`、`v1__test01__exp12__run001__step004000`、`v1__test01__exp13__run002__step020000`；字段均用明确分隔符，`run`至少三位补零、`step`至少六位补零。
- **`v1`只指研究模型版本**，不会随着实验编号/重复次数/训练步数自动增加；模型架构的代码revision、配置hash、原始MemoryVLA版与旧残差适配版的区别在manifest中明确记录。若用户批准新研究架构才另设V2，禁止Agent擅自生造`V12`这种版本。
- **`test01`**来自`Output/test_01`这样的测试序号；**`exp12`**是Experiment 12；**`run001`**是在同一实验内第1次**独立训练运行**，另一训练种子/从头重训/不兼容配置产生独立`run002`。同一运行的**暂停、断点续训、进程重启、作业重派、增加总步数**仍保持同一个`run001`，**不增加模型版本或run编号**；以`resume_event`/`attempt_id`单独记录恢复和工作台重试。
- **`step002000`**是从这次训练谱系起点累计的optimizer更新步数，不是microstep或单次恢复后的局部计数。严格续训到4000步，文件名应为同一运行的`...__step004000`；不能复位为2000、不能覆盖旧checkpoint。
- **推荐目录**：`Output/test_01/experiment_12/train_runs/run001/checkpoints/v1__test01__exp12__run001__step002000/`。FSDP分片、优化器、训练状态全部位于该checkpoint目录内；无论是单文件还是分片，目录/索引都使用规范ID。`latest`/`best`只允许作为指向真实ID的索引，不得替代实体名称。
- 在`checkpoint_index.csv`及工作台训练列表明确列出`model_version,test_id,experiment_id,run_id,optimizer_step,checkpoint_id,base_checkpoint,code_commit,config_hash,seed,data_manifest,job_id,attempt_id,resume_event,sha256,status`。启动前校验目录唯一、历史checkpoint只读。旧文件名保留别名映射，**不批量改名/覆盖已有产物**。
- **评估运行另设`eval_run_id`**，每个评估记录必须指向确切的`checkpoint_id`，不能用`V12权重`、`第13组权重`、`latest`等模糊标识替代。

细则与样例见 [references/checkpoint-naming.md](references/checkpoint-naming.md)。

## 三、用户资源与部署原则

当前用户确认的资源清单（**启动时必须用真实设备探测复核**）：

| 设备 | 用户声明的数量和显存 | 默认用途 |
|---|---|---|
| NVIDIA A100 | 4 张 × 80GB | 同步训练、模型推理 |
| NVIDIA RTX 4090 | 2 张 × 48GB | 模型推理、Isaac Sim / B1K 仿真评估 |
| NVIDIA RTX 6000 Ada | 1 张 × 48GB | 训练、模型推理、仿真评估 |

总计 **7 张 GPU**。用户偶尔口述“A6000”，在实际 `nvidia-smi`/UUID 核对之前不得当作新增的第八张卡；同理，用户给出的显存与驱动报告不同时，**按物理真实值作资源可行性判断并记录差异**。

- **训练：**当任务书指定“四卡”时，必须 4×A100 同步参与**一个**分布式作业。不能为推理擅自改3卡训练；不要把4个单卡作业称为4卡同步。计算与证明有效全局 Batch：`world_size × per_rank_micro_batch × grad_accum_steps`；检查代码中 `global_batch_size` 字段的真实语义。
- **并行共存与不中断续跑：**其他训练、评估或推理任务**正在运行并不是暂停/禁止恢复本实验的理由**，严禁设置“7张卡/4张A100必须全部空闲才允许续训”的全局空闲门槛。工作台先按GPU UUID检查**其他进程的峰值显存、当前剩余容量和计算吞吐**，若既有任务与本训练共享设备仍能安全共存，直接从原checkpoint继续；同机多任务须隔离端口、会话、目录、进程及资源配额。四卡同步作业仍需4个真实A100 rank，不能为了共存私自改成2卡/3卡或改有效Batch。若某张A100不能容纳所需FSDP峰值加安全余量，在工作台保留待续跑任务，**先执行其他可并行的推理/评估/数据处理工作，并在最早可用的安全时机自动恢复**；不要等待整个集群彻底空闲。用户任务优先，除非收到授权，不抢占、不杀死别的作业。
- **推理：**在用户允许的设备中，以工作台当前支持的入口和实时容量为准，优先复用匹配的就绪服务。需要共卡时，按显存峰值、推理 QPS 和对现有作业吞吐的影响选择设备。设备角色允许某用途时，仍要核对该用途是否已接入工作台。
- **仿真：**优先 2×4090、**每卡2环境，共4环境**；先实测单环境和双环境的显存、CPU、端口隔离、推理QPS、有效回合/小时。不可行就降低并发并解释，条件允许时再回到4环境。每个环境有独立策略/Memory会话、随机状态和产物目录。6000 Ada 可在任务安排与并发允许时补充仿真。
- **资源指标：**有真实可运行任务等待时，4张A100每卡**实际显存占用目标≥80%（80GB卡即至少64GB，可在有真实工作负载且留有安全余量时达到更高占用）**；4090及RTX 6000 Ada默认≥70%（48GB卡约33.6GB）；**不能通过空占显存凑数字**。实际优先级：实验正确性与不干扰已有作业 > 有效训练/评估吞吐 > 占用率。用每卡样本时间序列、队列和原因解释低占用，不因负载天然较小就伪造达标。

具体操作与排错，读取 [references/hardware-workbench.md](references/hardware-workbench.md)。

## 四、必须经由现有工作台

1. **训练、模型推理、仿真评估都经用户现有工作台的 `preview → 资源核对 → start` 或其真实等价接口启动和管理。** 实际接口与能力见仓库 [工作台手册](../../../../docs/workbench_agent.md) 及当前 API。若确实需要缺失的入口，优先扩展现有工作台并留回归验证。
2. 在工作台记录**job ID、服务会话、类别、宿主机、GPU UUID、代码和配置、数据和权重、状态、开始/结束时间、日志、检查点、结果路径**。正式作业与Agent探索性任务标记不同类别但统一可查。
3. 不得杀死或抢占用户正在运行的正式作业；不能隐藏OOM/断服务/作业失败或重复提交。所有重试必须幂等，可按任务唯一键去重。
4. 超过 2,000 个 optimizer steps 的训练须从**同一工作台**完成暂停、完整恢复和续跑验收。

## 五、训练执行与 checkpoint

- **正式训练**指 4×A100 同步执行的同一分布式作业，计划总预算为 **5,000 个 optimizer steps 及以上**。其余按用途登记为探索性验证或工程自检。
- **工程自检**仅指用于验证链路的临时训练，最多 **100 个 optimizer steps**。终态后先把结果、必要失败信息和作业 ID 记入本实验 `progress.md`，再经工作台删除该临时训练及其专用临时产物，确认训练列表已移除。清理前按作业 ID 和输出目录核对归属及依赖。
- 用官方仓库/当次任务书确认**模型初始化、参数冻结范围、Loss、optimizer、LR、weight decay、scheduler、BF16/FSDP、动作 horizon、记忆容量/检索层数、数据采样规则**。方法移植实验须先核对上游源码/commit；不能自行改为LoRA、冻结骨干、改训练目标，或者把某次实验的 `2e-5` 误认为所有 VLA 任务的通用LR。
- 同步训练前，做真实batch的前向、反向、连续optimizer step检查；验证所有预期可训模块进入 optimizer、梯度非零、参数真实变化，保存重载模型后前向可复现。Full FT显存不足时先评估合法工程策略（FSDP FULL_SHARD、checkpointing、减microbatch增累积、适用的offload），而不是擅自降级方法。
- `optimizer step` 不等于 microstep，必须记录 `world_size/microbatch/accum/effective_batch/seen_samples`；只比较相同样本口径的数据。训练总步数、评估频率、**checkpoint间隔以任务书指定为准**；当前用户对Exp12/13指定的是**每2000 optimizer steps保存一次**。
- **仅计划累计超过 2,000 个 optimizer steps 的训练强制支持严格续训**。可续训 checkpoint 完整保存模型、optimizer、scheduler、适用的 AMP/scaler、各 rank RNG、采样器和数据位置、累计步数及训练元数据，并使用原子写入或完成标记。经工作台验证暂停后释放配额、恢复同一训练状态并继续更新。计划最多 2,000 步的验证训练按任务保留所需权重并验证重载。
- 训练监控：总Loss、分身体部位Loss、LR、grad norm及clip、模块参数更新、每步耗时/吞吐、显存、OOM与错误。**训练Loss下降≠闭环成功率提升**。

更多验收证据和异常流程见 [references/training-resume.md](references/training-resume.md)。

## 六、推理、闭环评估与科研比较

1. **评估协议不可自行漂移：**保持任务书定义的任务/实例/seed、控制器、动作窗口、决策步数、成功判据、恢复状态以及模型checkpoint身份。B1K任务常用`n_action_steps=8`仅为历史惯例，必须以当前实验协议为准。
2. 区分**模型输出动作**、**仿真实际执行动作**、**物理真值**与**人工视频判定**。默认记录三相机观测、机器人状态/动作、时间戳、任务指令、模型输出、物理事件、录像、异常原因及回合唯一标识。
3. 历史记忆模型必须从**对应checkpoint自己的网络和原始顺序观测**重建其记忆状态；不要把其他checkpoint的memory tensor直接当作当前权重的历史。固定输入Normal/Empty/Wrong历史消融须控制当前RGB/本体/语言/感知历史及推理RNG，只改变明确定义的一类历史。
4. 机制诊断、离线Probe/MAE、候选动作变化与**真实闭环效果**分开报告。`Probe BA`、门控输出、历史差异、动作MAE都不能直接等价为阶段决策正确率。阶段行为需要物理真值、末端轨迹和视频共同核实；误触按钮和主动转向单列。
5. 有对照时优先保证**相同初始化来源、数据、训练预算、评估实例和协议**；原始官方无追加训练权重属于性能参考，同训练谱系/同预算的无记忆继续微调才可用于估计记忆的净增益。没有这种对照就标注限制。
6. 统计必须按**独立回合/独立实例**汇总，给出分子/分母、置信区间与物理判据；相邻决策帧不能冒充独立样本。对失败原因注明证据强度。

读取 [references/evaluation-reporting.md](references/evaluation-reporting.md) 获取指标和归档清单。

## 七、Agent 自适应巡检和可靠调度

- 长任务不能在提交之后停止监管，其他作业运行期间也必须继续判断是否可共享资源、何时安全恢复，不得只依据整机/全卡是否空闲来决定是否续跑。持续检查工作台作业状态、真实进度增量、checkpoint完成、队列、GPU、磁盘、推理QPS、仿真完成数与失败原因；**事件驱动优先，定时采样兜底**。典型采样1–5分钟，Agent实质巡检可随任务时长选2–5/5–15/15–30分钟，运行且有待办时原则上不超过30分钟。
- 对有待执行任务却连续空闲超过10分钟的GPU/服务主动调查、派发或记录真实阻塞。尽量对接**工作台既有调度器、回调、supervisor**；如不得已使用系统定时器，也必须保证作业从工作台可见、可暂停和可终止。不能依赖单个CLI会话一直开着或长`sleep`作为持久监管机制。
- 巡检状态和调度操作必须落盘、可重启恢复、去重；每次有明确下次检查时刻与理由。遇到严重NaN、错误训练谱系、权重/数据身份不明、Repeated OOM/评估错误时暂停问题作业并记录，不能悄悄改实验配置继续。
- 任务结束必须收尾：所有成功/失败/阻塞的工作均有证据；无有价值待办时允许退出，不为了“GPU占用率”无限生成随机任务。

## 八、统一交付与使用方式

- 产物按实际实验路径归档到 `Output/test_NN/experiment_NN/`。执行计划和进度遵循仓库实验看板规范。保留适用的 `report.md`、`MANIFEST.json`、作业配置/身份、`train_monitor.csv`、`checkpoint_index.csv`、`eval_trials.csv`、`resource_summary.csv`、视频/物理真值索引及运行、巡检记录。
- 最终用**完成/部分完成/阻塞/未执行**逐项验收，提供实际计数和原因；“提交了150回合”不等于“完成了150回合”，更不等于“成功了150回合”。
- 每次任务书只写研究特有的目标、数据、模型、训练配置及验收门槛，并写一句：**“训练、推理、评估、工作台资源调度、checkpoint、持续巡检、归档与复现均遵循 `robot-vla-experiment-ops` Skill。”**
- 需要独立任务单的最短模板见 [templates/experiment-task-template.md](templates/experiment-task-template.md)。
