# 人与 AI 共用的研究工作台方案

## 1. 要解决的问题

用户提出一个研究问题，AI 先查项目已有代码、资源、标准和实验结论，形成可审阅方案；确认后使用现有工作台完成代码检查、训练、推理和评估，最后回答研究问题并留下证据。研究题目由用户决定，不预设为检索归一化或任何一种模型改进。

例如：“检索模块改动后是否优于当前版本？请做配对短实验，每组不超过 100 步。”页面应直接说明比较什么、保持什么条件、复用什么入口、当前由谁处理、需要用户决定什么，以及最后有哪些证据。

本次交付为前端交互原型。AI 推理、代码修改、资源查询、任务执行及后台持久化均不在本次实现范围。模拟任务使用独立的浏览器存储，所有成绩、资源分配和代码审查状态都是示例。

## 2. 五类职责

| 职责 | 自主判断 | 固定操作 | 交接产物 |
| --- | --- | --- | --- |
| 研究规划 Agent | 理解问题、读已有研究、提出假设、设计对照与停止条件 | 按统一格式提交方案、检查预算和所需材料 | 研究任务、方案修订、判定依据、实验分支 |
| 代码工程 Agent | 实现想法、定位错误、解释变更；独立审查角色检查实现 | 管理隔离工作区、记录版本、生成源码快照、调用既有检查 | 变更集、审查意见、检查结果、源码快照 |
| 资源管理服务 | 必要时由 Agent 提出设备或预算调整建议 | 目录查询、能力匹配、占用核对、预留、排队、释放 | 资源请求与分配记录 |
| 实验执行服务 | 无法按既定方案继续时，返回可处理的异常 | 按依赖启动、等待、暂停、收集日志与产物、执行有限重试 | 运行状态、训练/推理/评估 ID、产物引用 |
| 评估分析 Agent | 判断可比性、解释结果、区分支持/不支持/证据不足、建议下一步 | 调用固定评估协议计算指标并关联对照 | 证据表、结论、局限、后续实验建议 |

五类职责不等于五个常驻大模型。初期使用三个判断角色（规划、代码、评估分析），资源和执行以服务为主。代码作者与审查者使用分开的任务上下文；代码作者不直接批准自己的修改。正式指标由评估程序产出，分析角色引用指标，不通过生成文本替代计算。

共享研究记录是一项数据能力，不再增加常驻 Agent。所有角色读取同一份想法、实验、失败原因、结论和证据。写作、文献专职角色等需求出现后再扩展。

## 3. 研究主线与交接

1. **交办问题**：输入研究问题、希望看到的证据，选择改进方法、诊断原因或评估已有权重；高级参数按需展开。
2. **准备方案**：检索已登记代码、数据、权重、协议和已有结论。缺少材料明确列为待补；不给未知路径编造可用状态。
3. **确认方案**：审阅实验分支、控制条件、预算、工作范围和复用入口。
4. **实现与审查**：需要改代码时，创建实验工作区，形成差异、检查结果和独立审查意见；仅评估任务跳过修改。
5. **资源与执行**：根据能力和占用分配资源，冻结运行身份，按既有流程完成检查、训练、推理和评估。仅评估任务不创建新训练。
6. **分析与归档**：分析角色基于固定协议的结果回答问题，保留负结果和不足，关联源码、配置、权重、数据划分和指标。
7. **下一轮**：提出新的研究任务，记录父任务和出发证据；不覆盖上一轮结果。

原型用显式按钮模拟各次交接，不通过定时器假装后台正在运行。按钮分别叫确认方案、通过代码审查、模拟分配资源、模拟完成实验、归档示例结论。

## 4. 自由探索与固定标准

自由部分：研究假设、实验设计、实现方法、错误诊断、结果解释。方案须说明变化因素、共享条件和预期证据，不要求所有任务使用同一种算法。

固定部分：版本记录、已有检查入口、资源目录和队列、任务状态、指标定义、数据划分与评估实例、日志与产物关联。规则通过版本化标准发布，作为运行的输入。

持续执行的后台规则采用事件驱动：

| 事件 | 固定动作 | 完成后的交接 |
| --- | --- | --- |
| 新代码变更进入审查 | 调用已登记检查，收集输出 | 返回代码审查角色；失败时不推进正式运行 |
| 已确认任务满足资源条件 | 分配并提交现有任务入口 | 更新运行状态 |
| 新训练权重就绪 | 按已批准协议安排对应评估 | 将指标交给评估分析角色 |
| 作业失败 | 保存失败证据，在预算内有限重试 | 重试耗尽后等待调整方案 |
| 指标与产物齐备 | 固定整理证据清单 | 请求分析并归档 |

“受控研究”在确认方案和代码以后按既定预算执行；“逐步确认”在每次交接等待用户。两种方式均保留固定标准，超出原方案需要新修订。本原型用手动推进展示两种方式，不执行实际后台自动化。

## 5. 共享数据模型与修改规则

网页和 AI 工具操作同一组记录，通过同一后端服务校验，避免维护两套参数和业务逻辑。

| 对象 | 主要内容 |
| --- | --- |
| ResearchTask | 问题、证据要求、父任务、责任角色、状态 |
| PlanRevision | 修订号、分支、控制条件、预算、范围、标准版本、用户决定 |
| ChangeSet / Review | 工作区、变更、检查、审查意见与结论 |
| StandardRevision | 默认预算、重试上限、协议定义、自动触发规则 |
| Run | 方案修订、标准快照、源码快照、资源分配、子任务 ID、当前状态 |
| Artifact / Finding | 指标、日志、权重及证据引用、研究结论 |
| Activity | 操作人或角色、动作、时间、对应对象 |

方案处于草稿时可编辑；已确认的方案再次修改会创建新修订并重新确认。已创建的运行保存原方案和标准快照，禁止通过页面编辑回写其历史身份。原型调整方案时会暂停当前模拟运行，保留历史记录，再创建修订草稿；真实系统接入时必须等待暂停结果后再切换运行。

修改共享标准只影响随后创建或明确重新生成的方案。现有方案仍显示原标准版本；已有运行始终使用当时的快照。人和 AI 不各自保存一份默认配置。

## 6. 复用当前项目的接入点

| 能力 | 当前代码/接口 | 后续接法 |
| --- | --- | --- |
| 训练配置、启动与控制 | `train/dashboard.py` 的 `TrainingManager`；`/api/training/options`、`preview`、`start`、`stop`、`resume` 等 | 共享服务封装已有方法，AI 与页面调用同一套参数校验 |
| 推理与 B1K 评估 | `groot_inference_launch.py`、`groot_web_launch.py`；`/api/inference/*`、`/api/launch/*` | 执行服务串联既有推理身份检查和评估任务 |
| 开发快测与其他 benchmark | `benchmark_dashboard.py` 的 `BenchmarkManager`；`/api/benchmarks/options`、`preview`、`start`、`stop` | 按能力目录绑定协议，不把不同 benchmark 的指标混为同一列 |
| 资源与已有产物 | `configs/workbench_devices.json`、各 Manager 的 options、`experiment_registry.py`、`/api/registry` | 将现有目录作为发现入口；补足资源分配记录而非新建平行资源库 |
| 代码版本与审查 | 现有源码注册/运行身份能力，加上待补的工作区与 Review 记录 | 源码快照关联实际变更；复用既有检查，允许登记新检查 |

未来工具可按职责提供 `research.find/create/revise`、`code.prepare_change/review/snapshot`、`resources.list/request`、`experiments.preview/submit/status/pause`、`evaluation.compare`、`findings.record`。这些是拟议工具名，并非当前已实现的 API。

强制复用依靠后端分发与运行身份：正式作业通过已登记入口提交，必须引用方案修订、源码和协议；Agent 提交结构化请求，服务调用原 Manager。提示词或 MCP 工具列表本身不能保证使用同一执行链路。代码开发可自由实现方法，正式训练评估不另建私有启动流程。

## 7. 前端信息架构

- **研究任务**：默认入口。左侧选任务，右侧显示问题、当前负责角色、下一步和三个页签：方案与决策、代码与执行、结果与证据。
- **角色与架构**：五类职责、自由与固定边界、交接产物、工具入口、人与 AI 共用后端的关系。
- **标准与自动化**：查看/修改示例标准版本、默认步数、预算上限、重试次数、自动触发规则。
- **研究记录**：查询已有结论与实验分支，点击返回对应任务，避免重复探索。

主任务页不展示无关 GPU 指标、固定的论文角色、示例大段终端日志或默认训练曲线；执行细节与运行身份按需展开。新建表单只要求问题和证据要求；设备、任务集合、训练预算等放在高级设置。

## 8. 分阶段落地与验收

1. **当前：前端评审**。完整方案与交互原型，验证新建、确认、审查退回、执行暂停、失败重试、修订留痕、结果归档、后续实验、标准版本和刷新恢复。无真实执行请求。
2. **共享数据与工具**。持久化上述核心对象，将页面中的规则统一到后端，封装现有 Manager 与资源目录。验收网页/工具创建的同一种任务可互相查看、编辑和追踪。
3. **固定流程接入**。完成检查到评估的依赖衔接、资源分配、状态恢复和产物关联。先用用户批准的单个受控任务验收。
4. **判断角色接入**。接入研究规划、代码工程和评估分析；检验是否先读已有记录、使用共享工具、留下可审阅产物，避免重复造轮子。

后续三阶段待页面与方案确认后实施。本次不引入新的工作流框架、不迁移项目、不启动真实实验。

## 9. 参考架构

- [RD-Agent](https://github.com/microsoft/RD-Agent)：借鉴实验生成、编码、运行、反馈与记录的固定交接。
- [AIDE](https://github.com/WecoAI/aideml)：借鉴候选实验及其父子关系，记录有效与失败的尝试。
- [autoresearcherUI](https://github.com/Fchaubard/autoresearcherUI)：借鉴规划、实施、审议和执行调度的职责分离；其多角色说明来自 README，未在本项目中运行验证。
- [ZenML MCP](https://github.com/zenml-io/mcp-zenml)：借鉴将已有实验平台能力作为 AI 工具暴露。
- [ClearML](https://github.com/clearml/clearml) 与 [dstack](https://github.com/dstackai/dstack)：借鉴实验身份、产物记录与资源队列；不要求整体迁移。
