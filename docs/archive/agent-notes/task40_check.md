# Agent 开发任务书：Task 40 分阶段智能评估体系与 VLA 快速迭代平台

## 一、总体目标

在现有 B1K-2025、GR00T N1.6、MemoryVLA 和 Body 研究项目基础上，开发一套能够长期复用的 **分阶段任务评价、失败归因与模型对比系统**。

现有评估主要依赖完整任务成功率、Q-score、任务进度和人工观看视频，存在以下问题：

1. 完整任务耗时长，无法频繁评估每个 checkpoint。

2. 任务进度无法充分反映操作质量。

3. 无法区分任务顺序错误、历史状态判断错误与物理操作失败。

4. 无法明确判断新增 Memory / Body 模块究竟改善了哪些环节。

5. 现有前端工作台的 VL 诊断功能较简单，未形成可用于科研迭代的完整评价体系。

**本任务的最终目标不是生成一份视频分析报告，而是建立可以反复使用的自动评估工具。**

期望工作流：

模型训练 → 仿真 Rollout → 自动提取阶段和物理状态 → VL 失败分析 → 生成指标 → 多模型比较 → 指导下一轮修改。

第一阶段只完整支持 Task 40，架构需要允许后续扩展到其他 B1K 任务。

---

## 二、首先调查现有项目，不要直接重写

Agent 首先检查现有仓库，定位：

- B1K-2025 Task 40 的任务定义、成功判据、任务状态及 Q-score 计算实现。

- OmniGibson 机器人、微波炉门、爆米花等对象的状态读取接口。

- GR00T 的 Rollout、动作记录、视频生成和 checkpoint 加载逻辑。

- 当前 Memory / Body 模块及其可选诊断输出。

- 当前工作台前端、后端 API、VL 视频诊断模块的实际代码。

- 已有评估数据和运行日志的存储格式。

优先复用已有逻辑，避免建立另一套独立系统。

正式修改前，生成简短的现状检查报告，列出可直接复用的模块、需要新增的功能和确实缺失的数据。

## 三、建立 Task 40 的细粒度任务模型

先不要简单沿用官方任务进度，将 Task 40 拆成以下 9 个原子阶段：

| 阶段  | 正确行为        | 主要判断内容                  |
| --- | ----------- | ----------------------- |
| S1  | 定位并前往厨房     | 是否到达正确区域、是否摔倒或陷入异常导航    |
| S2  | 优先选择微波炉     | 是否错误地先前往爆米花             |
| S3  | 靠近并选择打开微波炉门 | 是否错按启动按钮、是否正确操作门把手      |
| S4  | 拉开微波炉门      | 门是否真实达到打开状态             |
| S5  | 离开微波炉并前往爆米花 | 是否在门未打开时提前离开            |
| S6  | 抓取爆米花       | 是否正确接近、闭合夹爪、抓住并抬起       |
| S7  | 返回微波炉并放入爆米花 | 是否返回正确位置、门是否打开、物体是否真正放入 |
| S8  | 关闭微波炉门      | 门是否真实关闭                 |
| S9  | 按下启动按钮      | 是否在正确阶段按下、是否真正完成任务      |

这只是初始任务定义。需要结合 Task 40 官方场景、示教和任务成功条件检查并修正，不要直接把表格当作仿真真值。

每个阶段进一步定义：

- 前置条件 `precondition`

- 进入条件 `entry_condition`

- 预期动作 `expected_behavior`

- 完成条件 `success_predicate`

- 失败事件 `failure_events`

- 允许的下一阶段 `valid_transitions`

特别注意区分**动作尝试**与**物理结果**。

例如：

- 机器人做了拉门动作，不等于门打开。

- 夹爪闭合，不等于抓住爆米花。

- 爆米花进入微波炉附近，不等于成功放入。

- 机器人转向下一工位，不等于上一阶段成功。

阶段完成的历史事件和当前物理状态需要分别保存。比如门曾经打开过，不代表此刻仍然打开。

阶段模型使用独立配置文件实现，不要把 Task 40 的全部逻辑硬编码在前端或评估主程序里。

## 四、建立三层分析体系

### 第一层：仿真物理事实层

尽可能直接从 OmniGibson 获取：

- 机器人位置、姿态、底盘运动状态

- 是否跌倒或处于异常姿态

- 微波炉门关节位置及开合状态

- 爆米花位置、抓取关系、放置关系

- 夹爪和机械臂状态

- 官方任务谓词及完成状态

优先使用物理状态判断阶段是否真正完成。

如果某个物理状态无法可靠读取，需要记录为 `unknown`，不能假设成功或失败。

所有事件与动作、视频使用统一仿真时间戳。

### 第二层：VL 视频行为分析层

复用当前已有的 VL 分析模型。

VL 不需要判断整个视频的一个最终分数，而是分析具体事件前后的短视频片段。

优先分析：

- 机器人选择了哪个区域或目标

- 是否尝试拉门、抓取、放置、按按钮

- 是否重复无效动作

- 是否在操作尚未完成时离开

- 是否发生不符合任务顺序的阶段转换

- 是否存在无法确定的模糊行为

推荐先从仿真状态变化、机器人运动变化和夹爪事件产生候选时间窗口，再调用 VL 分析。

避免每一帧都调用 VL，控制评估时间和模型调用成本。

VL 必须输出结构化 JSON，包含：

`episode_id、time_start、time_end、stage_id、observed_behavior、error_type、confidence、evidence_frames、explanation`

VL 只能根据实际可见行为判断，不允许臆测 GR00T 内部的真实意图。

### 第三层：失败归因层

至少区分以下错误类型：

| 错误类型      | 示例                       |
| --------- | ------------------------ |
| 导航与定位错误   | 找错厨房、异常移动或摔倒             |
| 任务顺序决策错误  | 应该开门却先去拿爆米花              |
| 当前状态判断错误  | 门就在视野里且未打开，却提前转入下一阶段     |
| 历史状态利用错误  | 门离开视野后，模型没有正确利用之前观察到的门状态 |
| 机械臂操作执行失败 | 正确尝试拉门，但没有真正拉开           |
| 抓取或接触失败   | 夹爪闭合但未抓住物体               |
| 停滞或重复操作   | 长时间反复执行无效动作              |
| 无法判断      | 证据不足以明确归因                |

必须同时记录：

**首次失败原因**和**后续衍生错误**。

例如 S4 拉门失败，S5 提前离开，S7 隔着门放置，应记录一个操作失败事件，以及后续错误阶段转换事件，不能简单算成三个互不相关的独立失败。

Memory 和 Body 只作为后续需要检验的改进方向，不能预先规定所有决策错误都由 Memory 负责、所有操作失败都由 Body 负责。

## 五、建立比 Q-score 更细粒度的评价指标

保留 B1K 官方完整成功率和 Q-score，不修改官方逻辑。

另外新增研究用的诊断指标：

**1. 阶段到达率（Stage Reach Rate）**

成功达到某个阶段进入条件的 Episode 比例。

**2. 阶段执行成功率（Stage Execution Success Rate）**

在实际尝试该阶段的样本中，满足物理完成条件的比例。

**3. 错误阶段转换率（Invalid Transition Rate）**

阶段前置条件未满足，却开始执行后续阶段动作的比例。

**4. 关键决策正确率（Decision Accuracy）**

在具有明确任务前置条件的选择时刻，机器人是否选择符合任务顺序的行为。

**5. 首次失败分布（First Failure Distribution）**

统计首次关键失败集中在哪个阶段、属于哪种类型。

**6. 完整任务成功率**

沿用 B1K 官方最终完成判据。

另外可输出自定义阶段完成比例作为诊断曲线，但必须命名为 `Custom Stage Completion`，不能冒充官方 Q-score。

统计时明确区分未到达、已到达、已尝试、已完成、失败和未知。所有比例必须报告分子、分母和有效样本数。

### 必须调查当前 Q 值只有 0/1 的问题

追踪当前项目的：

- Q 值计算代码

- 官方 B1K Q-score 实现

- 任务成功标志和任务进度计算

- 逐步记录到最终前端显示的转换过程

重点判断：

1. 读取的是官方 Q-score，还是二值 success？

2. 当前是否只在 Episode 结束时计算？

3. 是否有任务谓词、数值类型或聚合逻辑的问题？

4. Task 40 当前任务定义本身是否导致该指标只能取少数值？

输出源码路径、公式和实测轨迹。

如属于正常的官方指标行为，应说明原因，不要为追求密集分数而修改官方 Q-score。

## 六、建立快速评估机制

这是本任务的重要工程目标。

### 1. 支持复用已有 Rollout

优先直接分析现有视频和日志。

不能因为增加新的诊断系统，就要求所有已有模型重新进行完整评估。

对于旧 Rollout 缺失的物理状态，允许通过视频分析给出低置信度判断，并清楚标记证据不足。

### 2. 新 Rollout 增加轻量诊断记录

在现有评估过程中同步保存必要的机器人状态、关键物体状态、动作和事件。

尽量避免重复运行仿真。

### 3. 支持早期诊断

对于明显失败的 Episode，例如机器人已经摔倒或持续长时间重复无效操作，允许在诊断模式下提前终止并记录原因。

提前终止不能被当作正式完整任务评估结果；正式评估仍保持官方终止逻辑。

### 4. 可选的局部阶段测试

调查 OmniGibson 是否能保存与恢复完整仿真状态。

如果可行，后续支持从指定阶段前的物理状态启动短程测试，快速评价抓取、开门、放置等操作。

此功能先做可行性检查，不要因它阻塞主评估系统。

## 七、改造现有工作台 UI

**直接增强并替换现有工作台的 VL 诊断功能。不要重新开发独立的网页，不要破坏现有训练、评估和模型管理功能。**

先检查现有前后端项目架构，沿用其技术栈、组件规范和 API 风格。

新的 VL 诊断页面至少包含：

### 1. 评估概览

可以选择：

- Task（首版仅 Task 40 完整支持）

- 模型类型（GR00T / Memory / Memory + Body）

- Checkpoint

- 评估批次和 Episode

展示任务成功率、阶段到达率、错误转换率、阶段执行成功率及主要失败类型。

### 2. Episode 分析页面

提供可交互的阶段时间轴。

点击 S1～S9 中的任意阶段，应能：

- 自动跳转到相应视频位置

- 查看阶段开始、完成或失败时间

- 查看对应三路相机画面

- 查看物理状态判定

- 查看 VL 分析结论和证据

- 查看首次失败及后续错误的关联

### 3. 模型对比页面

在相同任务、测试实例和评估设置下，比较不同模型：

- 阶段到达率差异

- 阶段执行成功率差异

- 错误阶段转换率差异

- 不同失败类型的占比

- 最终完整任务成功率

必须显示样本量，避免少量 Episode 造成误导。

### 4. 人工复核功能

用户可以对 VL 的阶段判断和错误归因执行：

- 确认

- 修改

- 标记不确定

修正结果保存到独立标注文件，用于后续校准评估规则，不要覆盖原始仿真数据或原始模型输出。

### 5. 结果导出

支持导出 JSON、CSV、Markdown 汇总报告，包括各 Episode 的阶段时间线及证据。

## 八、让评价体系真正支持 Memory / Body 迭代

完成基础评估以后，再增加以下分析能力。

### Memory 相关

在模型支持时记录：

- 每个决策时刻 Memory 是否有历史

- 当前保留的历史时间范围和槽位来源

- 检索注意力、门控和融合信息

- 正确历史、空历史、错误历史的离线动作对比

重点观察：错误跳阶段、忘记先前物体状态、重复操作是否减少。

注意：注意力可视化不等于真正理解历史，应该结合固定当前输入的历史干预实验。

### Body 相关

如果当前模型支持 Body 结构输入或 Body-conditioned Retrieval，则记录：

- 本体状态、相关关节和末端位姿

- 实际动作与关节限制

- 不同身体部件使用的历史信息

- 具体操作阶段的动作预测和执行结果

重点检验 Body 模块是否改善与运动学构型、可达性及检索相关的决策。

不要把碰撞、抓取失败等所有低层控制问题自动归因于 Body 检索。

### 迭代实验规范

后续每次修改 Memory 或 Body 时：

1. 固定基础权重、训练数据、测试实例和评估协议。

2. 记录具体修改及其要解决的错误类型。

3. 先进行短训练与离线检查。

4. 选择少量候选 checkpoint 进行仿真。

5. 用相同的评价工具比较新旧模型。

6. 只有出现可复现收益，再扩大测试规模。

同时区分：

- 开发集：允许反复调试。

- 保留测试集：不用于选择网络和 checkpoint，用于最终性能确认。

不要未经确认自动反复修改大量网络模块，造成无法归因的实验结果。

## 九、其他 B1K 任务如何扩展

采用**通用评估引擎 + 单任务阶段配置**的方案。

Task 40 先做完整实现。

对于后续 Task 0、34 或其他任务：

1. Agent 根据官方任务定义及成功示教，自动生成阶段划分草案。

2. 人类专家确认阶段顺序、前置条件和完成条件。

3. Agent 尽量自动关联可用的仿真物理谓词。

4. 用少量成功和失败视频校准 VL 分析。

5. 通过同一评估引擎运行。

不要求人工对所有数据逐帧标注。

没有经过专家确认的任务配置应标记为草案，不能直接进入正式科研统计。

## 十、开发执行顺序与验收

请分四个阶段完成，不要一次性堆积所有功能。

### P0：现有系统与 Q-score 调查

交付：

- 现有评估与前端结构说明

- Task 40 真实任务状态和对象接口调查

- Q 值仅有 0/1 的原因

- 可用数据与缺失数据清单

### P1：Task 40 阶段分析引擎

交付：

- Task 40 阶段配置

- 物理状态判定

- VL 事件与失败分类

- 单 Episode 时间线

- 先对 3～5 条 Episode 进行人工核查

**验收：能够明确区分“拉门失败”和“门未打开却进入下一阶段”。**

### P2：批量统计与前端替换

交付：

- 现有 Rollout 批量分析

- 阶段和错误统计

- 工作台新的 VL 诊断页面

- 模型对比、人工复核和结果导出

- 至少 20 条 Episode 的试运行结果（优先复用已有数据）

**验收：能直接在工作台中选择 Episode，查看每个阶段的判定、视频证据和失败原因。**

### P3：支撑科研迭代

交付：

- Memory / Body 可选诊断日志接入

- checkpoint 与评估批次关联

- 新旧模型配对比较

- 自动生成模型改进建议报告

- 可扩展到其他任务的配置模板

**验收：修改一次 Memory 或 Body 后，无需重新开发分析脚本，就能在工作台中得到针对各个阶段的性能差异。**

## 十一、开发约束

1. 不修改 B1K 官方 Q-score、任务成功条件和物理规则。

2. 保留已有 GR00T、Memory、Body 权重与训练配置。

3. 评估系统和模型训练系统尽量解耦。

4. 优先复用已有 VL 模型，不额外部署新模型。

5. 所有指标必须可追溯到原始仿真记录或视频证据。

6. 对无法判断的事件使用 `unknown`，不得强行分类。

7. 所有代码修改应包含必要的测试和运行说明。

8. 不允许为提高评价分数修改仿真成功条件。

9. 首版重点实现 Task 40，不要过度设计 50 个任务的完整配置。

10. 先完成评价系统并通过验收，再考虑模型结构修改和大规模训练。

## 十二、最终需要达到的效果

我希望以后每次评估 GR00T、Memory 或 Memory + Body，都能够直接看到：

**这个模型在哪些阶段做对了、哪些阶段做错了、是选择错误还是操作失败、Memory 是否改善了历史状态判断、Body 是否改善了对应操作决策，以及这些变化是否最终提升了任务成功率。**

最终系统应该成为整个 Memory + Body 研究项目的长期评估基础设施，而不只是一次性的 Task 40 视频分析脚本。
